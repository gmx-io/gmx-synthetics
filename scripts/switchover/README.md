# Market hours switchover

Cron-driven switching of market params between on-hours and off-hours states
(commodities, SPCX/NYSE).

Switch instants come from `schedule.txt`, generated by the risk oracle, so DST,
exchange holidays and early-close days are data in that file rather than crontab
arithmetic. The cron no longer has a built-in expiry date — but the file does: when
it runs out, switching stops. See "Regenerating the schedule".

## How it works

- `setup_cron.sh` installs a single crontab entry running `runScheduled.js` every
  minute (idempotent); `uninstall_cron.sh` removes it.
- `runScheduled.js` reads the schedule, works out the state each market should be in
  right now (the last transition at or before now) and acts only where that differs
  from what `state/` records.
- Ticks are serialised by `flock -n` in the crontab entry, not by the runner. The kernel
  drops that lock on any exit including a kill, so it cannot wedge. **Run it the same way
  by hand** — `flock -n scripts/switchover/state/.cron.lock node scripts/switchover/runScheduled.js`
  — or a manual run can collide with the cron one and burn a nonce.
- `switchover.env` supplies `WRITE`/`CLI` (non-interactive, actually sends) and the
  `INCLUDE_*` groups to the hardhat script. The runner refuses to start if it is missing
  or lacks `WRITE=true`/`CLI=true`: without them every switch silently reports
  "read-only mode" and nothing moves.
- `markets.js` maps each calendar to its markets and on-chain addresses. This is
  membership, not schedule: it changes only when a market is added or retired.
- Plain CommonJS on the repo's Node (`.nvmrc`), no build step and no new dependencies —
  it reuses `scripts/monitor/utils.js` for Telegram and the healthcheck ping, the same
  way the monitors do. Nothing to install beyond the repo's own `yarn install`.
- State is per market (`state/<chain>_<SYMBOL>.state`) and advances only after the switch
  succeeds, so a market that failed is retried on the next tick while the
  ones that succeeded are left alone.
- On the first run for a market it records the state **without** sending a transaction
  and says so in telegram. Verify the on-chain state once after installing — see
  "Recovery".
- `--dry-run` prints what would happen: no transactions, no state writes, no telegram.
  It does create `state/` and, under the cron wrapper, competes for the same lock — a
  dry run while a switch is in flight simply does nothing.
- Logs go to `logs/switchover/run_scheduled.log` (timestamped, trimmed to the last 10000
  lines) and, via the crontab entry, `logs/switchover/cron.log` for anything the runner
  could not write itself.
- Each switch runs `updateMarketConfig.ts` with `MARKET_STATE=onHours|offHours`
  (off-hours = main config block merged with the market's `closedState` overrides in
  `config/markets.ts`). The per-market `*_open.sh` / `*_closed.sh` wrappers are gone —
  their three environment variables live in `markets.js`.
- Markets on the risk oracle app (rwa_v1) set `SWITCHOVER_ONLY=true` in their
  `markets.js`, so this cron writes **only** `positionFeeFactor`
  for them. Every other switchover param (OI, position impact, min collateral,
  borrowing) is switched by the risk oracle. `positionFeeFactor` stays here
  because the GMX `RiskOracleConfig` rejects `POSITION_FEE_FACTOR`
  (`InvalidBaseKey`) and the risk oracle can't post it. All Arbitrum RWA markets
  (GOLD, SILVER, WTIOIL, BRENTOIL, NATGAS, SPCX) are on the risk oracle and set
  this flag.
- A switch reports to Telegram: the transaction hash on success, the reason and the
  tail of the output on failure. A run that sends no transaction counts as failed, so
  `closedState` must differ from on-hours in at least one key — for risk-oracle markets
  that key is `positionFeeFactor`, the only one `SWITCHOVER_ONLY` writes.
- Holidays need no special handling: a day the exchange is shut simply has no rows in
  `schedule.txt`, so nothing fires and the market keeps its off-hours params. The old
  `run_nyse.sh` wrapper and its hand-maintained `nyse_holidays.txt` are gone — early
  closes, which that list could not express at all, are now ordinary rows.

## Requirements

Node as pinned in `.nvmrc` (22), the repo's `yarn install`, and `flock` (util-linux) on
the cron host. No build step. `setup_cron.sh` bakes the directory of the `node` it was
run with into the crontab entry, because cron's own `PATH` does not include an nvm
install — run it from a shell where `node` already works.

Environment (from the repo's `.env`, as the monitors do):

| Variable | Meaning |
|---|---|
| `SWITCHOVER_TG_MESSAGES` | `true` to report to Telegram; anything else logs instead |
| `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID` | required when the above is `true` |
| `SWITCHOVER_SCHEDULE_FILE` | default schedule path; `--schedule` overrides it |
| `SWITCHOVER_HEALTHCHECK_URL` | optional dead-man's-switch, pinged only on a clean tick |

## Regenerating the schedule

`schedule.txt` is generated by the risk oracle and committed here, so a host only needs
to pull. Regenerate it from the risk oracle repository and commit the result:

```bash
just script switchover_schedule --start <YYYY-MM-DD> --end <YYYY-MM-DD> \
  --out <this repo>/scripts/switchover/schedule.txt
```

The runner reads `scripts/switchover/schedule.txt` by default; `setup_cron.sh <path>`,
`--schedule <path>` or `SWITCHOVER_SCHEDULE_FILE` point it elsewhere. It alerts if the
file is absent or unreadable, so a lost schedule is noisy rather than silent.

**Start at least one day before today.** Every calendar needs a transition at or before
"now", or the runner treats it as not covering the present and freezes its markets. CME
opens the evening before its trading date, but NYSE opens at 13:45Z on the day itself —
so a file generated with `--start` = today is already too late for NYSE any time before
that. `--start`: the runner refuses a schedule that begins in the
future (and says so in telegram) rather than inferring a state from it. When in doubt
use `--months N` instead of explicit dates.

The file's open times already include the oracle's own open delay and its closes are
the exchange's own, so both systems switch at the same instants. Which markets follow
which calendar lives in `markets.js` — update it when a
market is added or retired; the runner warns if the oracle lists a market it has no
mapping for.

`runScheduled.js` warns in telegram once a day when under 14 days of schedule remain,
and alerts once a calendar runs out — at that point its markets are frozen on their last
state while the oracle keeps switching everything else. Horizon is tracked per calendar,
so one exhausted calendar does not hide behind another.

## Recovery

State lives in `state/<chain>_<SYMBOL>.state` and holds `onHours` or `offHours` — what
the runner believes was last applied on-chain. It is a record of intent, not a reading
of the chain.

- **Force a market to be re-applied**: write the *opposite* value, e.g.
  `echo onHours > state/arbitrum_SPCX.state` when it should be off-hours. Deleting the
  file does **not** work — a missing file means "first run" and only seeds the state
  without sending a transaction.
- **See what a tick would do** without touching anything: `node
  scripts/switchover/runScheduled.js --dry-run`.
- **Check the actual on-chain state**: run `updateMarketConfig.ts` for the market with
  the state you expect, without `WRITE`/`CLI`; `no changes to apply` means it is already
  there. (The runner treats that same message as success and advances its state, so a
  market fixed by hand heals on the next tick rather than alerting forever.)
- **After switching a market by hand** (see below), update its state file to match, or
  the next transition will be computed from stale history.
- **Rolling back this runner** to its bash predecessor is clean if ever needed: the
  `state/<chain>_<SYMBOL>.state` format is unchanged and the schedule file is not in git,
  so `git revert` plus `setup_cron.sh` restores the previous scheme without losing state.
  Rolling back further, to the fixed-time cron, is not supported: `run_nyse.sh` and
  `nyse_holidays.txt` were deleted and that holiday list is stale anyway.

## If a switchover fails

```bash
# enable
MARKET=0x470128853D74dab7423904a20eA5AA230e9e561B \
MARKET_STATE=onHours \
npx hardhat run scripts/updateMarketConfig.ts --network arbitrum

# disable
MARKET=0x470128853D74dab7423904a20eA5AA230e9e561B \
MARKET_STATE=offHours \
npx hardhat run scripts/updateMarketConfig.ts --network arbitrum
```

For a risk-oracle market add `SWITCHOVER_ONLY=true` so the run
touches only `positionFeeFactor`.

A "no changes to apply" error means the market is already in the target state.
